### 3.3. Число 304 в разных системах счисления

```text
dec=304 oct=460 hex=130
a=304 b=304 c=304, all equal: yes
```

`304`, `0460` и `0x130` — три записи одного значения. Восьмеричная запись
начинается с `0`, шестнадцатеричная — с `0x`. Двоичная запись `0b...`
появилась в C23; в C17 она является расширением GCC и при `-pedantic-errors`
не принимается.

### 3.4. Степени двойки и единицы объёма

Программа выводит `2^0 ... 2^20`, а также `2^32` и `2^48` в `uint64_t`:

```text
2^0  = 1
...
2^10 = 1024
2^20 = 1048576
2^32 = 4294967296
2^48 = 281474976710656
2^64 = 18446744073709551616 (does not fit uint64_t; UINT64_MAX = 18446744073709551615)
```

`2^64` не помещается в `uint64_t`, поэтому печатается пояснение, а не
«значение типа». Связь с состояниями: `N` бит дают `2^N` комбинаций.
Например, 8 бит — 256 состояний, 16 бит — 65536, 32 бита — 4294967296.

Единицы:

```text
8 бит = 1 байт
1 КиБ = 1024 Б
1 МиБ = 1024 КиБ = 1048576 Б
1 ГиБ = 1024 МиБ = 1073741824 Б
```

КиБ/МиБ/ГиБ — степени 1024; кБ/МБ/ГБ — степени 1000. Смешивать их без
пояснения нельзя.

## 4. Массивы и неинициализированная память

### 4.1. Неинициализированные автоматические массивы

`experiments/arrays.c`, собранный с `-DUNINIT_DEMO` и `-O0`, на одном запуске
показал:

```text
chars[0..7]    = 10 0 0 0 0 0 0 0
integers[0..7] = 0 0 1872291488 1 1872291570 1 -164659024 1
reals[0..7]    = 4.17246e-314 7.8804e+115 4.16264e-314 0 0 0 4.16264e-314 0
```

**Важно:** это не результат, определённый стандартом. Автоматический объект
без инициализатора имеет indeterminate value; чтение такого значения может
быть undefined behavior. Значения зависят от компилятора, оптимизации,
состояния стека и предыдущих вызовов. Использовать их как «остатки памяти»
нельзя.

### 4.2. Исправленная версия

После `= {0}` массивы заполняются осмысленно. Размеры:

| Массив | `sizeof(array)` | `sizeof(element)` | Число элементов |
|---|---:|---:|---:|
| `char chars[304]` | 304 | 1 | 304 |
| `int integers[25]` | 100 | 4 | 25 |
| `double reals[25]` | 200 | 8 | 25 |

Число элементов считается как `sizeof(array) / sizeof(array[0])`, а не
«магической константой». `char`-массив выводится таблицей шириной 10
элементов; числовые массивы — по одному элементу в строке.

## 5. Одинаковые символы в разных целочисленных типах

Массивы `char`, `short`, `int`, `unsigned long long` с кодами `MAI304`:

```text
char:               MAI304
short:              MAI304
int:                MAI304
unsigned long long: MAI304

sizeof(a)=7 sizeof(b)=14 sizeof(c)=28 sizeof(d)=56
elements: a=7 b=7 c=7 d=7
```

`sizeof` растёт пропорционально размеру элемента. При попытке `%s`:

```text
%s on char array:               "MAI304"
%s on short array (cast):       "M"
%s on int array (cast):         "M"
%s on unsigned long long array: "M"
```

Только `char`-массив с завершающим `\0` является C-строкой. Для `short`/`int`/
`unsigned long long` `%s` читает байты: на little-endian первый байт `'M'`,
затем нулевой байт старшей части элемента — вывод обрывается. Это не
преобразование массива в строку, а случайное байтовое совпадение. На
big-endian результат был бы другим; передавать такие массивы в `%s` нельзя.

## 6. `printf`, ввод и управляющие последовательности

### 6.1. Спецификаторы

```text
one integer: dec=304 oct=460 hex=130 HEX=130
address of local variable: 0x16d5be97c
```

`%d` — `signed int`, `%u` — `unsigned int`, `%o` — восьмеричное,
`%x`/`%X` — шестнадцатеричное, `%c` — символ, `%s` — C-строка,
`%f` — `double` в `printf`, `%p` — указатель, `%zu` — `size_t`.

### 6.2. Управляющие последовательности

```text
AAA	BBB
firstSECOND
one
quote: "C" and slash: \
```

- `\t` — табуляция;
- `\r` — возврат каретки: `SECOND` перезаписывает начало `first`;
- `\0` — нулевой символ: `printf("one\0two\n")` печатает только `one`,
  потому что C-строка заканчивается на первом `\0`;
- `\\` и `\"` — экранирование обратного слеша и кавычки;
- `\a` — bell, эффект зависит от терминала.

### 6.3. `scanf` и проверка результата

Корректный ввод:

```text
Enter int, unsigned int, double: number=42 unsigned=7 real=3.500
```

Некорректный ввод:

```text
Enter int, unsigned int, double: Invalid input: expected int, unsigned int, double
exit status = 1
```

Проверяется, что `scanf` вернул ровно 3; иначе программа сообщает об ошибке
в `stderr` и завершается с ненулевым кодом.

### 6.4. Маленькие ловушки

- `switch` и `int` — зарезервированные слова (keywords); объявить переменную
  с таким именем нельзя.
- Для hosted-программы используется `int main(void)` или
  `int main(int argc, char *argv[])`; `void main(void)` нестандартен.
- Во всём проекте используется один стиль фигурных скобок (K&R).

## 7. Операторы, токены и undefined behavior

### 7.1. `a+++b` и `b---a`

Максимальный «жадный» разбор токенов:

```text
a+++b  ->  a ++ + b  ->  (a++) + b
b---a  ->  b -- - a  ->  (b--) - a
```

При `a = 5`, `b = 7`:

```text
a+++b is a ++ + b, result=12, a is now 6
b---a is b -- - a, result=1, b is now 6
```

### 7.2. `a = b++ + ++b`

В выражении `b` изменяется дважды (`b++` и `++b`) без упорядочивания между
этими изменениями. Стандарт C не определяет результат; это undefined
behavior. Поэтому выражение не выполняется и «правильное число» для него не
приводится: такого числа нет.

### 7.3. Таблица безопасных выражений

При `x = 5`, `y = 3`, `z = 2`, `w = 1`:

| Выражение | Результат | Комментарий |
|---|---:|---|
| `x + y * z` | 11 | `*` раньше `+` |
| `(x + y) * z` | 16 | скобки меняют смысл |
| `x << y - z` | 10 | `-` раньше `<<` |
| `(x << y) - z` | 38 | скобки меняют смысл |
| `x < y == z` | 0 | `<` раньше `==` |
| `x & y == w` | 0 | `==` раньше `&` |
| `(x & y) == w` | 1 | скобки меняют смысл |
| `x ^ y & z` | 7 | `&` раньше `^` |
| `(x ^ y) & z` | 2 | скобки меняют смысл |
| `x && y || z` | 1 | `&&` раньше `\|\|` |
| `x \|\| y && z` | 1 | `&&` раньше `\|\|` |
| `(x \|\| y) && z` | 1 | скобки меняют смысл |

## 8. Побитовый регистр устройства

`experiments/register_demo.c`:

```text
initial        dec=  0 hex=0x00 bin=00000000
set POWER      dec=  1 hex=0x01 bin=00000001
set READY      dec=  3 hex=0x03 bin=00000011
set TX         dec= 11 hex=0x0B bin=00001011
toggle ERROR   dec= 15 hex=0x0F bin=00001111
ERROR is set: yes
clear ERROR    dec= 11 hex=0x0B bin=00001011
toggle READY   dec=  9 hex=0x09 bin=00001001
mask 1u << 4   dec= 25 hex=0x19 bin=00011001
RX is set: yes
```

Операции:

```c
reg |= mask;              /* set   */
reg &= (uint8_t)~mask;    /* clear */
reg ^= mask;              /* toggle*/
(reg & mask) != 0;        /* test  */
mask = (uint8_t)(1u << n);/* build */
```

В реальном устройстве такие биты могут включать режимы, отражать готовность,
ошибку, передачу и приём. Поэтому `<<`, `>>`, `&`, `|`, `^`, `~` — рабочий
инструмент низкоуровневого ПО, а не только «математические приёмы».

## 9. Циклы, `enum`, `switch`, progress bar и checksum

### 9.1. Стадии

```c
enum LabStage {
    STAGE_FOR,
    STAGE_WHILE,
    STAGE_DO_WHILE,
    STAGE_BITS,
    STAGE_DONE
};
```

Диспетчер — `switch (stage)`; каждая стадия переходит к следующей. Стадии
`for`, `while`, `do...while` обрабатывают по `5 500 000` значений, каждая
использует результат в общем `checksum`. Дополнительная стадия `bits` тоже
обрабатывает `5 500 000` значений и использует регистр устройства.

Объём: `5 500 000 × 64` раунда = `352 000 000` внутренних итераций на стадию;
четыре стадии — `1 408 000 000` итераций. `sleep()` не используется.

### 9.2. Progress bar

Фрагмент вывода (в терминале строки перезаписываются через `\r`; здесь
показаны характерные кадры):

```text
for          [------------------------------]   0%
for          [###############---------------]  50%
for          [##############################] 100%
while        [------------------------------]   0%
while        [###############---------------]  50%
while        [##############################] 100%
do-while     [------------------------------]   0%
do-while     [###############---------------]  50%
do-while     [##############################] 100%
bits         [------------------------------]   0%
bits         [###############---------------]  50%
bits         [##############################] 100%
```

`fflush(stdout)` нужен потому, что строка не заканчивается `\n`; без сброса
буфера вывод может оставаться в буфере и «анимация» не появится.

### 9.3. Итоговые значения

Маска `completed`:

## 10. Три способа измерения времени

Один и тот же участок «прогрузки» измерялся тремя таймерами одновременно:
`time()`/`difftime()`, `clock()`/`CLOCKS_PER_SEC`, `gettimeofday()`.

### 10.1. `-O0`

```text
time/difftime:        10 s
clock/CLOCKS_PER_SEC: 9.614105 s
high-resolution:      9.619794 s
```

Внешнее время процесса:

```text
real 9.89
user 9.56
sys  0.05
```

### 10.2. `-O2`

```text
time/difftime:        2 s
clock/CLOCKS_PER_SEC: 2.088128 s
high-resolution:      2.089103 s
```

Внешнее время процесса:

```text
real 2.37
user 2.08
sys  0.00
```

### 10.3. Сравнение

| Сборка | `time`/`difftime` | `clock` | high-resolution | `real` | Размер файла |
|---|---:|---:|---:|---:|---:|
| `-O0` | 10 s | 9.614105 s | 9.619794 s | 9.89 s | 37 080 Б |
| `-O2` | 2 s | 2.088128 s | 2.089103 s | 2.37 s | 36 136 Б |

`time()` имеет дискретность в целую секунду, поэтому даёт грубые `10` и `2`.
`clock()` измеряет процессорное время процесса, а high-resolution — реальное
время. Для однопоточной CPU-bound программы они близки. Небольшое расхождение
с `real` — накладные расходы ОС, буферизации и обновления progress bar.

`-O2` быстрее примерно в `9.89 / 2.37 ≈ 4.2` раза. Checksum совпадает:
`0x443f7bd7960f30d0`. Размер `-O2` немного меньше, но на нём сказываются и
`-g`, и конкретные оптимизации; делать вывод «-O2 всегда меньше» нельзя.
Оптимизация может менять наблюдаемое поведение программ с UB, поэтому UB
нельзя использовать как «тест памяти».

## 11. Локальные, глобальные, `static`, `extern`, `auto`

### 11.1. Связь между файлами

`device.h`:

```c
extern unsigned long global_runs;
void device_tick(void);
unsigned long device_internal_calls(void);
```

`device.c`:

```c
unsigned long global_runs = 0;       /* внешняя связь */
static unsigned long internal = 0;   /* только внутри device.c */

void device_tick(void)
{
    static unsigned long calls = 0;  /* живёт всю программу */
    ++global_runs;
    ++internal;
    ++calls;
}
```

`main.c` обращается к `global_runs` через объявление из `device.h`. Попытка
обратиться к `internal` напрямую:

```c
extern unsigned long internal;
```

приводит к ошибке компоновки:

```text
Undefined symbols for architecture arm64:
  "_internal", referenced from:
      _main in ccwSPEQh.o
ld: symbol(s) not found for architecture arm64
```

Это и есть внутренняя связь: имя известно только внутри `device.c`.
Функция `device_static_calls()` возвращает значение локального `static`
счётчика, не раскрывая сам объект.

Глобальные объекты — не «моральная категория». Фраза «глобальные переменные
всегда зло» слишком категорична: в embedded/static-memory системах глобальное
или `static`-хранилище часто осознанно используют для состояния устройства,
буферов и таблиц с предсказуемым временем жизни. Практический компромисс —
скрывать внутреннее состояние в file-scope `static` и давать наружу
минимальный интерфейс. `volatile` может понадобиться для MMIO/ISR, но сам по
себе не делает доступ потокобезопасным.

### 11.2. `auto` в C17 и C23

`experiments/c23_auto.c`:

```c
auto value = 304;
auto ratio = 1.5;
```

| Стандарт | Результат |
|---|---|
| C17 | FAIL: `type defaults to 'int' in declaration of 'value'` |
| C23 | PASS |

В C17 `auto` — только storage-class specifier: `auto int local_value = 304;`
задаёт автоматическое хранение, а типа нет. В C23 появился вывод типа по
инициализатору, поэтому `auto value = 304;` работает. `register` —
историческая подсказка компилятору; современный оптимизатор сам распределяет
регистры, и гарантировать «жизнь в регистре» нельзя.

## 12. `const` и `#define`

```c
#define BUFFER_SIZE 304
const size_t buffer_size = 304;
```

`BUFFER_SIZE` — текстовая подстановка препроцессора, не объект. `buffer_size`
— типизированный объект с областью видимости и временем жизни. Оптимизатор
может убрать `const`-объект из бинарника, поэтому «`const` всегда занимает
память» — упрощение.

### 12.1. Макросы и скобки

```text
BAD_SQUARE(2 + 3)  = 11
GOOD_SQUARE(2 + 3) = 25
```

`BAD_SQUARE(x) x * x` раскрывается в `2 + 3 * 2 + 3`; `GOOD_SQUARE(x)`
раскрывается в `((2 + 3) * (2 + 3))`. Но даже «правильные» скобки не делают
макрос функцией: `GOOD_SQUARE(i++)` раскрывается в `((i++) * (i++))` и
изменяет `i` дважды без упорядочивания — это UB. В одном запуске получено
`30`, `i = 7`; это наблюдение, а не переносимый результат.

### 12.2. Stringify, token pasting и `DEBUG`

```text
STRINGIFY(BUFFER_SIZE)  = BUFFER_SIZE
XSTRINGIFY(BUFFER_SIZE) = 304
CONCAT(var, 1) = var1 = 42
```

`#x` не раскрывает макрос перед строкизацией; двухуровневый `XSTRINGIFY`
раскрывает. `##` склеивает токены: `CONCAT(var, 1)` → `var1`.

Без `-DDEBUG`:

```text
DEBUG is not defined: DEBUG_LOG expands to ((void)0)
```

С `-DDEBUG`:

```text
DEBUG: debug logging is enabled
DEBUG is defined: DEBUG_LOG expands to fprintf(stderr, ...)
```

Условная компиляция удаляет код на этапе препроцессора; runtime `if` оставляет
обе ветви в программе.

## 13. Стандарты C и флаги GCC

### 13.1. `__STDC_VERSION__`

```text
GCC 16 без -std:  __STDC_VERSION__ = 202311
c90:              __STDC_VERSION__ is not defined
c99:              199901
c11:              201112
c17:              201710
c23:              202311
```

GCC 16 по умолчанию использует GNU C23. На другом компиляторе значение может
отличаться; стандарт в сравнительных экспериментах задаётся явно.

### 13.2. Матрица возможностей

| Возможность | Режим | Результат |
|---|---|---|
| `//` и `int i` в `for` | C90 | FAIL |
| `//` и `int i` в `for` | C99 | PASS |
| `_Static_assert` | C99 | FAIL |
| `_Static_assert` | C11 | PASS |
| `0b100110000` | C17 | FAIL |
| `0b100110000` | C23 | PASS |
| `auto x = 304` | C17 | FAIL |
| `auto x = 304` | C23 | PASS |

Сборка выполнялась с `-Wall -Wextra -Wpedantic -pedantic-errors`, поэтому
расширения GCC не маскировали ошибки.

### 13.3. Флаги

| Флаг | Назначение |

## 14. От исходника к исполняемому файлу

`make manual` (или `scripts/build_steps.sh`) выполняет:

```text
gcc -E main.c -o main.i
gcc -E -P main.c -o main_no_lines.i
gcc -S main.c -o main.s
gcc -c main.c -o main.o
gcc -c device.c -o device.o
gcc -c timer.c -o timer.o
gcc main.o device.o timer.o -o vpd_lab2
```

| Расширение | Что это |
|---|---|
| `.c` | исходный текст C |
| `.i` | результат препроцессора |
| `.s` | ассемблерный текст компилятора |
| `.o` / `.obj` | объектный файл |
| exe / executable | результат компоновки |

Полученные размеры:

```text
main.i            1330 строк, 277 line markers
main_no_lines.i    650 строк
main.s            3738 строк
```

В `main.i` видны раскрытые `#include` и макросы. Например, `WORK_ITEMS`
раскрывается в `5500000ULL`:

```text
for (uint64_t i = 0; i <
                            (
                            5500000ULL
                            )
```

В `main_no_lines.i` нет строк-маркеров `#`, поэтому файл удобнее читать как
обычный текст. Флаг `-P` не «убирает стандартные библиотеки» — он подавляет
только line markers.

В `main.s` находится функция `main` (на Darwin — `_main`):

```asm
.globl _main
_main:
LFB11:
	.loc 1 252 1
	sub	sp, sp, #64
...
	bl	_demo_types
```

## 15. Makefile и CMake

### 15.1. Makefile

Основные правила:

```make
$(TARGET): $(OBJ)
	$(CC) $(CFLAGS) $(LDFLAGS) $^ -o $@

obj/%.o: %.c | obj
	$(CC) $(CPPFLAGS) $(CFLAGS) -c $< -o $@
```

- `$@` — имя цели (например, `obj/main.o` или `vpd_lab2`);
- `$<` — первая зависимость (исходный `.c`);
- `$^` — все зависимости (все `.o` при линковке).

Есть цели `run`, `bench`, `bench-run`, `manual`, `experiments`, `standards`,
`lab1`, `clean`. `bench` собирает `-O0` и `-O2` в разные каталоги `obj/o0` и
`obj/o2`, чтобы объектные файлы не перезаписывали друг друга.

### 15.2. CMake

```cmake
cmake_minimum_required(VERSION 3.20)
project(VPD_Lab2 LANGUAGES C)

set(CMAKE_C_STANDARD 17)
set(CMAKE_C_STANDARD_REQUIRED ON)
set(CMAKE_C_EXTENSIONS OFF)

add_executable(vpd_lab2 main.c device.c timer.c)
target_compile_options(vpd_lab2 PRIVATE -Wall -Wextra -Wpedantic)
```

Сборка:

```bash
cmake -S . -B build
cmake --build build
./build/vpd_lab2
```

CMake использовал генератор `Unix Makefiles` и AppleClang 16.0.0 (build type
не задан), собрал `build/vpd_lab2` (34 952 Б).
Прогон: `real 10.24`, `clock 9.939136`, `high-resolution 9.940263`,
checksum `0x443f7bd7960f30d0` — совпадает с Make-сборкой.

### 15.3. Сравнение

| GNU Make | CMake |
|---|---|
| читает `Makefile` и выполняет правила/команды | читает `CMakeLists.txt` и генерирует build-system |
| правила зависят от shell/ОС | помогает описывать кроссплатформенный проект |
| прозрачно показывает зависимости файлов | удобнее масштабируется на цели, библиотеки, платформы |
| не является компилятором | тоже не является компилятором |

## 17. `foreach` в C и C++

В C отдельной конструкции `foreach` нет; используется обычный цикл:

```c
for (size_t i = 0; i < count; ++i) {
    printf("%d\n", values[i]);
}
```

В C++ есть range-based `for`:

```cpp
for (const auto value : values) {
    std::cout << value << '\n';
}
```

`experiments/foreach.cpp` выводит `10 20 30 40 50`. «foreach» — идея обхода
коллекции, а конкретный синтаксис зависит от языка.

## 18. Выводы

1. **Ручная сборка** (`gcc -E`, `-S`, `-c`, линковка) показывает каждый этап:
   препроцессор → компилятор → ассемблер → объектный файл → компоновщик.
   Это самый прозрачный, но самый трудоёмкий путь.
2. **GNU Make** автоматизирует те же команды и зависимости, но правила всё
   равно выполняются в shell и часто зависят от ОС.
3. **CMake** не заменяет компилятор: он генерирует build-system и удобнее
   масштабируется, но добавляет слой конфигурации.
4. **Стандарт C важен**: `//`, `for (int i...)`, `_Static_assert`, `0b...`,
   `auto x = ...` появляются в разных версиях. Один и тот же исходник может
   собираться в C23 и не собираться в C17.
5. **Реализация важна**: на Apple arm64 `long double` — 8 байт, `long` — 8,
   а `gcc` по умолчанию — Apple Clang. Размеры и `__STDC_VERSION__` нельзя
   считать «вечными константами».
6. **UB нельзя использовать как результат**: неинициализированные массивы,
   `a = b++ + ++b`, `GOOD_SQUARE(i++)` дают наблюдения, а не переносимые
   значения. `-O2` может менять поведение таких программ.
7. **Время**: `time()` грубый, `clock()` — процессорное, high-resolution —
   реальное. Для CPU-bound однопоточной программы `clock()` и
   high-resolution близки; `-O2` ускорил работу примерно в 4.2 раза при
   одинаковом checksum.
8. **Связь между файлами**: `extern` даёт доступ к глобальному объекту,
   `static` на file scope скрывает состояние внутри модуля, `static` внутри
   функции сохраняет значение между вызовами. Это практичный способ
   организовать состояние устройства с минимальным публичным интерфейсом.
